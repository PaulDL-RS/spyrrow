# spyrrow 1.0 design

Status: draft for maintainer review. Branch `design/v1`, base = spyrrow 0.10.0
ported to sparrow 0.3.0 (rev `3be9158`) / jagua-rs 1.0.0.

Decisions that are really the maintainer's call are marked **[MAINTAINER]** and
collected in section 9.

## 1. Goals and non-goals

### Goals

1. **Follow sparrow / jagua-rs vocabulary and semantics.** jagua-rs 1.0 made
   several things explicit that spyrrow 0.x papered over: rotation modes
   (`discrete` / `stepped` / `continuous`), reflection axes, a
   `min_item_separation` that belongs to the *instance*, `ExtTransformation`
   with a `reflected` flag, warm starting from a solution, a richer
   `SolutionListener`. The 1.0 API is a thin, typed, Pythonic projection of those
   concepts, so that the sparrow paper, the sparrow CLI and spyrrow share one
   mental model and one JSON format.
2. **No surprising defaults or sentinels.** `None` must not mean "free rotation",
   `[]` must not mean `[0]`, a config object must not silently store a random seed.
3. **Every breaking change is explicit and listed** (section 4), and **0.x stays
   usable** as `spyrrow.v0` for one major version (section 5).
4. **One coherent design for the features currently drafted as additive 0.x
   branches** (reflection, stepped rotation, warm start, JSON export, detailed
   progress events, advanced knobs) instead of five bolt-ons.
5. **Better ergonomics and diagnostics**: validated, immutable value objects;
   a real exception hierarchy; `KeyboardInterrupt` that works; results that say
   how the run went (seed used, run time, feasibility, interruption).
6. Keep CI/packaging effort proportional: no new build targets, fewer wheels if
   possible.

### Non-goals (for 1.0)

* Not a rewrite of sparrow's algorithm or a re-implementation of any solver
  logic in Python. The Rust layer stays a thin shell around `sparrow::optimizer::optimize`.
* No support for what jagua-rs 1.0 itself rejects for strip packing items: holes,
  multipolygons, quality zones (`min_quality`). The API leaves room for them
  (`Item.shape` is a polygon today), nothing more.
* No bin packing (`jagua-rs` `bpp`), no async/`asyncio` API, no multi-instance
  batch API. `solve()` is blocking and releases the GIL; users bring threads.
* No logging bridge, no shapely extra in the draft (proposed in section 8).

## 2. Architecture and packaging

### Layout (maturin mixed project)

```
Cargo.toml                lib name = "_core"
pyproject.toml            [tool.maturin] python-source = "python", module-name = "spyrrow._core"
src/lib.rs                #[pymodule] _core: registers everything below
src/engine.rs             v1 solve engine (JSON in / JSON out, events, errors)
src/terminator.rs         v1 terminator (stop flag + rate-limited Ctrl-C probe)
src/v0.rs                 the 0.x pyclasses and glue, frozen (almost verbatim 0.10.0)
python/spyrrow/__init__.py        1.0 public API, re-exports
python/spyrrow/model.py           Rotation, Item, StripPackingInstance, PlacedItem, StripPackingSolution
python/spyrrow/config.py          SolverConfig, Preset and the sparrow sub-configs
python/spyrrow/events.py          progress events
python/spyrrow/errors.py          exception hierarchy
python/spyrrow/_engine.py         the only module that talks to _core
python/spyrrow/_geometry.py       pure-Python helpers (min height per orientation, hull)
python/spyrrow/v0/__init__.py     the 0.x API (re-exports frozen native classes, emits DeprecationWarning)
python/spyrrow/v0/__init__.pyi    the old stub
python/spyrrow/_core.pyi, py.typed
```

### Why a Python layer on top of a small native core

* The value objects (`Item`, instance, configs, solution, events) are
  `@dataclass(frozen=True, slots=True, kw_only=...)`: validation in
  `__post_init__`, `repr`, `==`, `hash`, `copy`, `pickle`, `dataclasses.replace`,
  inline type annotations and docstrings for Sphinx, all for free. In 0.x each of
  these needed hand-written Rust (`__deepcopy__`, `__repr__`, a hand-maintained `.pyi`
  that can drift from the code).
* The native surface shrinks to a handful of functions exchanging **JSON strings in
  jagua-rs/sparrow's own external format** (`ExtSPInstance`, `ExtSPSolution`) plus a
  resolved config JSON. Consequences: (a) Rust never needs to be touched for pure
  API ergonomics; (b) the Python objects round-trip *exactly* to what the sparrow
  CLI reads and writes (`ExtSPOutput`); (c) sparrow/jagua changes surface as a serde
  error in one place instead of as drift between hand-written pyclasses.
  The JSON round trip costs milliseconds even for thousands of items, versus
  minutes of solving.
* **Defaults are read from sparrow, not copied.** `_core.sparrow_defaults()` serializes
  `DEFAULT_SPARROW_CONFIG` (+ the `DEFAULT_*` early-termination constants) and
  `spyrrow.config` builds its dataclass defaults from it at import time. When
  `scripts/sync_sparrow.py` bumps sparrow, spyrrow's defaults follow automatically.
  (A drift test compares them against the Rust side.)
* Items cross the boundary with a dense internal index; user ids (`int` or `str`)
  are mapped back in Python.

### The v0 module

`src/v0.rs` is the 0.10.0 `lib.rs` moved and renamed, not refactored: same
pyclasses, same `#[pyo3(signature)]`, same serde output, its own copy of the old
terminator. Rationale: "reproduces 0.x exactly" is cheapest to *guarantee* by not
re-implementing it; it never changes (so there is no maintenance cost besides sparrow
API bumps in one `optimize(...)` call), and removing it in 2.0 is `git rm src/v0.rs
python/spyrrow/v0`. The pyclasses are registered in `_core` as `V0Item`, ... with
`module="spyrrow.v0"` and re-exported under their old names by
`spyrrow/v0/__init__.py`.
(The pure-Python alternative, re-implementing 0.x on top of the new API, was
rejected: `to_json_str()` byte-compat, `set_all` attributes, overflow errors for
`u8`/`u64` arguments, `int`-seconds semantics, etc. would each need re-checking.)

### abi3 **[MAINTAINER]**

Proposal: `pyo3 = { features = ["abi3-py310"] }`. Because the native layer is now
tiny and uses no abi3-incompatible API, a single `cp310-abi3` wheel per platform
replaces one wheel per (platform x Python 3.10-3.14 x PyPy). Impact on CI: the
matrix of jobs (platform/arch) stays identical, but each job builds sparrow
**once** instead of once per interpreter that `--find-interpreter` discovers
(on `ubuntu` runners typically 4-5), cutting wheel build time and PyPI storage
roughly 4-5x, and new Python releases need no new wheels. Costs: PyPy
is not supported by abi3 (the 0.x classifier "PyPy" is therefore dropped; sparrow's
speed makes PyPy irrelevant but check whether anyone uses it), free-threaded CPython
builds need their own wheel until abi3t exists, and a negligible slow-down of C-API
calls that this package does not do in hot loops. No code in this draft depends on
the choice, you can revert by deleting the feature.

### Versioning **[MAINTAINER]**

Cargo `1.0.0-alpha.1` (PEP 440 `1.0.0a1`). Reasons for a pre-release first: (1) `pip
install spyrrow` ignores pre-releases, so 0.x users are never moved by accident while
the API is reviewed; (2) the draft has not been exercised on the full CI matrix or by
real users; (3) the 1.0 tag should promise API stability for the sparrow knobs, which
should be validated with Jeroen first. `spyrrow.__version__` is read from the
installed distribution metadata (PEP 440), not from `CARGO_PKG_VERSION`.

### CI impact

No redesign. `maturin generate-ci`-style workflow stays; what changes: wheel installs in the test
steps get `--pre` (while the version is `1.0.0a1`, pip would otherwise pick the 0.x release from PyPI
instead of the wheel in `dist`);
`tests/` now contains `tests/v0/` (the old suite, long budgets), so `pytest -n auto`
runs both; pytest is configured with `--import-mode=importlib` because both folders
contain files with the same basename. Wheel tests install `spyrrow` from `dist` as
before and need no new dependency. Consider running `tests/v0` on `x86_64` jobs only
(e.g. `pytest tests/v0 -m ...`) if CI time matters; not done here.

## 3. Public API of spyrrow 1.0

Everything below is importable from `spyrrow` unless noted. Mapping column = the
sparrow/jagua concept mirrored.

| spyrrow 1.0 | mirrors |
|---|---|
| `Rotation` (`discrete` / `stepped` / `continuous` / `none`) | jagua `ExtRotation` |
| `Item(id, shape, demand=1, *, rotation, reflection_axes)` | jagua `spp::ExtItem` (+ `ExtOrientation` flattened) |
| `StripPackingInstance(strip_height, items, *, name, min_item_separation)` | `ExtSPInstance` |
| `PlacedItem(item_id, translation, rotation, reflected=False)` | `ExtPlacedItem` + `ExtTransformation` |
| `StripPackingSolution` | `ExtSPSolution` (+ seed, feasibility, interruption) |
| `SolverConfig`, `Preset` | `SparrowConfig`, sparrow CLI modes (`-x`) |
| `spyrrow.config.ExplorationConfig / CompressionConfig / SeparatorConfig / SampleConfig / ShrinkDecay / CDEConfig / ShapeConfig` | sparrow `ExplorationConfig`, `CompressionConfig`, `SeparatorConfig`, `SampleConfig`, `ShrinkDecayStrategy`, jagua `CDEConfig`, import tolerances |
| `spyrrow.events.*` | sparrow `SolutionListener` callbacks, `ReportType`, `OptimizationPhase`, `SeparationProgress`, `SeparationResult` |
| `spyrrow.errors` | `anyhow` errors of import / `optimize`, SIGINT |

### 3.1 `Rotation`

```python
Rotation.none()                  # only 0 degrees  == discrete([0.0])
Rotation.discrete([0, 90, 180])  # explicit list of degrees; zero is NOT implicit (jagua)
Rotation.stepped(45)             # 0, 45, ..., 315 ; step must divide 360
Rotation.continuous()            # any angle
Rotation.from_allowed_orientations(x)   # migration helper: None -> continuous, [] -> none, list -> discrete
```
Frozen, hashable; attributes `mode` (`"discrete" | "stepped" | "continuous"`),
`angles`, `step`. Validation mirrors jagua (finite, `0 < step <= 360`, step divides
360, at most 65 536 angles).

### 3.2 `Item`

```python
Item(id: int | str, shape: Sequence[tuple[float, float]], demand: int = 1, *,
     rotation: Rotation | Sequence[float] = Rotation.none(),
     reflection_axes: Sequence[float] = ())
```
* `rotation` also accepts a plain sequence of degrees (shorthand for
  `Rotation.discrete`). `None` is rejected with an explanatory error.
* `reflection_axes` is jagua's field verbatim (degrees, ccw from the item's x axis;
  `[0]` means "may be mirrored: (x, y) -> (x, -y)"). Empty = never reflected.
  Several axes are allowed (jagua takes the union of the orientations they generate); axes are
  only checked for being finite.
* Immutable, hashable, `dataclasses.replace(item, demand=3)` to derive variants.
  Validates: id type, >= 3 points, finite coordinates, `demand >= 1`, non-zero area.
  The closing point may be repeated (as in 0.x).
* `item.area`, `item.to_dict()`, `Item.from_dict()`.

Example:

```python
import spyrrow
tri = spyrrow.Item("tri", [(0, 0), (1, 0), (1, 1)], demand=6,
                   rotation=spyrrow.Rotation.stepped(90), reflection_axes=[0])
```

**Reflection caveat (verified in sparrow 0.3.0 sources):** sparrow only reads
`allowed_orientations().rotations()` and never `rotations_after_reflection()`, so
`reflection_axes` is accepted and validated by jagua-rs but never used: `PlacedItem.reflected` is
always `False` today. The API carries it (the JSON format, `PlacedItem.transform` and warm-start
import already handle it) so that it works as soon as sparrow uses it; it is documented as such in
the docstring. Upstream ask for Jeroen; tests must not expect reflected placements.

### 3.3 `StripPackingInstance`

```python
StripPackingInstance(strip_height: float, items: Sequence[Item], *,
                     name: str = "", min_item_separation: float = 0.0)
```
* `min_item_separation` moves here (jagua `ExtSPInstance.min_item_separation`,
  singular, `float`, `>= 0`, default `0.0` instead of `None`).
* Validates unique ids and **item-vs-strip feasibility** (TODO.txt wish): for every
  item the minimum extent over its allowed rotations/reflections (exact for discrete
  and stepped modes, rotating calipers over the convex hull for continuous) must fit
  **strictly** `strip_height - min_item_separation` (sparrow 0.3.0 fails with "could not construct an
  initial placement" when an item is exactly as high as the strip), otherwise `InvalidInstanceError` names the
  item. An empty item list is allowed and solves to the empty solution (as in 0.x).
* Methods: `solve(config=None, *, initial_solution=None, on_event=None, events=...,
  on_interrupt="raise") -> StripPackingSolution`, `validate(config=None)` (runs the real
  jagua-rs import: shape validity, self-intersections, ...), `to_dict()/from_dict()`,
  `to_json_str()/from_json_str()` (**sparrow CLI input format**), `total_item_area`,
  `total_demand`. Files: `spyrrow.read_json(path) -> (instance, solution | None)` and
  `spyrrow.write_json(path, instance, solution=None)`; a file holding a solution is the
  sparrow CLI output and can be used as a warm start by both tools.

### 3.4 `SolverConfig`, presets and sub-configs

```python
SolverConfig(*, time_limit: float | timedelta = 600, exploration_ratio: float = 0.8,
             num_workers: int | None = None, seed: int | None = None,
             exploration: ExplorationConfig = ..., compression: CompressionConfig = ...,
             cde: CDEConfig = ..., shape: ShapeConfig = ...)
SolverConfig.from_preset(Preset.AUTO, time_limit=60, seed=0)
SolverConfig.from_phase_times(exploration=48, compression=12, ...)   # 0.x pair mode
cfg.replace(seed=1)
```
* **Time**: one total budget (`time_limit`, seconds as `float` or `timedelta`) and
  one explicit `exploration_ratio` (sparrow's `DEFAULT_EXPLORE_TIME_RATIO`). The
  0.x three-way "total xor (exploration and compression)" rule disappears; the pair
  form is `time_limit=e + c, exploration_ratio=e / (e + c)` (helper provided).
* **Presets** (TODO.txt "presets as enums"): `Preset.AUTO` = sparrow with early
  termination (`max_conseq_failed_attempts=10`, failure-based shrink decay 0.9),
  which is the 0.x default and sparrow CLI `-x`; `Preset.EXHAUSTIVE` = sparrow
  defaults, spends the whole budget. Only presets that sparrow itself defines are
  shipped; speed/quality presets (`QUICK`, `GREEDY`, ...) need benchmark data first
  (section 9).
* `seed=None` stays `None`; the seed actually used is returned in
  `solution.seed`, so any run can be reproduced.
* `num_workers=None` = all logical cores (0.x behaviour; see open question).
* Power-user sub-configs, same field names as sparrow, defaults taken from sparrow:
  `ExplorationConfig(shrink_step, max_conseq_failed_attempts, solution_pool_distribution_stddev,
  large_item_ch_area_cutoff_percentile, separator)`, `CompressionConfig(shrink_range,
  shrink_decay: ShrinkDecay, separator)`, `SeparatorConfig(iter_no_imprv_limit,
  strike_limit, sample_config)`, `SampleConfig(n_container_samples, n_focussed_samples,
  n_coord_descents)`, `ShrinkDecay.time_based()` / `ShrinkDecay.failure_based(ratio)`,
  `CDEConfig(quadtree_depth, cd_threshold)`, `ShapeConfig(simplify_tolerance,
  narrow_concavity_cutoff)`. `n_workers` is hoisted to `SolverConfig.num_workers`
  (exploration and compression always share it); `log_level` is not exposed.
  The surrogate settings of `CDEConfig` are not exposed yet.

### 3.5 `solve`, warm start, events, interruption

```python
sol = instance.solve(SolverConfig(time_limit=30, seed=1))
better = instance.solve(SolverConfig(time_limit=60), initial_solution=sol)   # warm start

def on_event(ev):
    if isinstance(ev, spyrrow.events.SolutionReported) and ev.feasible:
        print(f"{ev.elapsed:6.1f}s width={ev.solution.width:.3f}")
instance.solve(config, on_event=on_event)
```
* **Warm start** = sparrow `optimize(..., initial_solution)`. The solution must place
  every item exactly `demand` times with known ids (checked in Python) **and be feasible for the instance**, separation included (checked in
  Rust with sparrow's `CollisionTracker`: sparrow 0.3.0's exploration stores the start as the first
  feasible solution and may return it unchanged, so an infeasible start would silently be returned);
  both errors are `InvalidSolutionError`; it can come from a previous `solve`, from
  `StripPackingSolution.from_json_str`, or from a sparrow CLI output file.
* **Events** replace the polled `ProgressQueue`. `on_event(event)` is called *from the
  thread that called `solve`* (the solver releases the GIL otherwise), so no
  thread-safety work is needed by the user, and users who prefer polling just
  `queue.put(event)` in the callback. Event classes (frozen dataclasses with
  `elapsed: float` seconds since the start of `solve`):
  `PhaseStarted(phase)`, `SolutionReported(kind: ReportKind, solution)` (with
  `.feasible`, `.phase`), `SeparationProgress(strip_width, density, iteration, min_loss)`,
  `SeparationFinished(success, duration, total_evals, total_moves, iterations)` (`duration` is
  sparrow's `elapsed_seconds`, renamed to avoid a clash with the event's own `elapsed`),
  `CompressionStep(shrink_step)`. `events=` selects which classes are delivered
  (default: `PhaseStarted`, `SolutionReported`, `CompressionStep`; the per-iteration
  separation events are opt-in because they are frequent).
* **Stopping**: raising `spyrrow.StopSolving` in a callback stops the solver
  gracefully, `solve` returns the best solution with `interrupted=True`. Any other
  exception stops the solver and propagates unchanged out of `solve`.
* **Ctrl-C**: raises `SolveInterrupted` (a `KeyboardInterrupt` subclass) carrying the
  best feasible solution found so far in `.solution`; `on_interrupt="return"` returns
  that solution (with `interrupted=True`) instead, which is the 0.x behaviour. Works
  when `solve` runs in the main thread. Note that sparrow checks the time limit only between separator strikes, so runs overrun the budget
  somewhat (about 10% observed in release builds, more in debug builds); `time_limit` is a target, not a hard deadline.
  The signal probe is rate-limited (50 ms)
  instead of acquiring the GIL on every `Terminator::kill` poll.

### 3.6 `StripPackingSolution` and `PlacedItem`

```python
PlacedItem(item_id, translation: tuple[float, float], rotation: float, reflected: bool = False)
  .transform(points) -> list[tuple[float, float]]   # reflect (y -> -y), rotate ccw (deg), translate
StripPackingSolution(width, strip_height, density, placed_items: tuple[PlacedItem, ...],
                     feasible: bool, run_time: float, seed: int | None, interrupted: bool)
  .to_dict() / .to_json_str(instance=None) / .from_dict() / .from_json_str()
```
`reflected` and `rotation` have exactly jagua's meaning (reflect the original local y,
then rotate, then translate; coordinates are the *original* item coordinates).
`to_json_str(instance)` writes the sparrow CLI output (`ExtSPOutput` = instance +
solution), loadable by `sparrow -i` for warm starting. `run_time` is measured from the
start of `solve` (jagua's `run_time_sec` is relative to a process-global epoch that is
meaningless in a library; and integer seconds).

### 3.7 Errors (`spyrrow.errors`, re-exported at top level)

```
SpyrrowError(Exception)
 +-- InvalidInstanceError(SpyrrowError, ValueError)   bad item / instance / jagua import failure
 +-- InvalidConfigError(SpyrrowError, ValueError)
 +-- InvalidSolutionError(SpyrrowError, ValueError)   unusable warm start
 +-- SolverError(SpyrrowError, RuntimeError)          sparrow failed (e.g. no initial layout)
 +-- SolveInterrupted(KeyboardInterrupt)              Ctrl-C, `.solution`
StopSolving(Exception)                                 raised by callbacks to stop gracefully
```
Dual inheritance means 0.x code that catches `ValueError` / `RuntimeError` keeps working.

### 3.8 JSON

`to_dict`/`from_dict`/`*_json_*` produce and consume the jagua-rs / sparrow external
format: `{"name", "min_item_separation", "strip_height", "items": [{"id", "demand",
"orientation": {"rotation": {"mode": ...}, "reflection_axes": [...]}, "shape":
{"type": "simple_polygon", "data": [[x, y], ...]}}]}`. Integer ids are written
verbatim; if any id is a `str`, ids are written as positions and the original id in an extra
`"label"` field (ignored by sparrow, restored by `from_dict`). This replaces the
0.x `to_json_str` formats, which were private serde dumps of the Rust structs (and
needed `tests/utils.py` to be converted to the sparrow format).

## 4. Breaking changes 0.x -> 1.0

All of them are avoided by `import spyrrow.v0 as spyrrow` (section 5).

| # | 0.x | 1.0 | Why | Migration |
|---|---|---|---|---|
| 1 | `import spyrrow` is the 0.x API | `import spyrrow` is the 1.0 API; 0.x lives in `spyrrow.v0` | clean top-level namespace | `import spyrrow.v0 as spyrrow` |
| 2 | `Item.allowed_orientations: list[float] \| None` (`None` = free, `[]` = `[0]`) | `Item.rotation: Rotation` (explicit modes) | sentinels were surprising; jagua has explicit modes | `Rotation.from_allowed_orientations(old)` or `None` -> `Rotation.continuous()`, `[]` -> `Rotation.none()`, list -> list |
| 3 | `allowed_orientations` mandatory 4th positional | `rotation` optional, **keyword-only**, default `Rotation.none()` | 2 required args are enough; physical parts default to fixed orientation | pass `rotation=` by keyword |
| 4 | `Item` mutable (`item.demand = 3`) | frozen / hashable | validation invariants, thread safety | `dataclasses.replace(item, demand=3)` |
| 5 | `Item.shape` list, `placed_items` list | tuples | immutability | `list(...)` if a list is needed |
| 6 | `Item.demand` required | default `1` | ergonomics (additive) | none |
| 7 | `Item.id: str` | `int \| str` | jagua ids are `u64` | none (strings still fine) |
| 8 | no reflection | `Item.reflection_axes`, `PlacedItem.reflected` | jagua 1.0 | additive; `PlacedItem.transform` applies it |
| 9 | `PlacedItem.id` | `PlacedItem.item_id` | `ExtPlacedItem.item_id` | rename |
| 10 | `StripPackingInstance(name, strip_height, items)` | `StripPackingInstance(strip_height, items, *, name="", min_item_separation=0.0)` | `name` is irrelevant for most users | use keywords |
| 11 | `StripPackingInstance` mutable, `items` list | frozen, `items` tuple | as 4 | rebuild the instance |
| 12 | `StripPackingConfig.min_items_separation` (`None`) | `StripPackingInstance.min_item_separation` (`0.0`) | jagua: it is a property of the instance | move the argument |
| 13 | `StripPackingConfig` | `SolverConfig` | different structure, avoid silent misuse of the old name | see rows below |
| 14 | `total_computation_time` / `exploration_time` / `compression_time` (int s, mutually exclusive combos) | `time_limit` (float s or `timedelta`) + `exploration_ratio=0.8`; `SolverConfig.from_phase_times` | no tricky combination rule, fixed 80/20 is a parameter | `time_limit=old_total`; pair -> `from_phase_times` |
| 15 | `early_termination: bool` (default `True`) | `Preset.AUTO` (default) / `Preset.EXHAUSTIVE`, or sub-config fields | maps to two sparrow settings, not one flag | `early_termination=False` -> `SolverConfig.from_preset(Preset.EXHAUSTIVE, ...)` |
| 16 | `quadtree_depth` on config | `config.cde.quadtree_depth` | sparrow `CDEConfig` | `cde=CDEConfig(quadtree_depth=...)` |
| 17 | `seed=None` replaced by a random seed stored in the config; attribute readable | stays `None`; actual seed in `solution.seed` | config no longer lies; same config object can be reused with fresh seeds | read `solution.seed` |
| 18 | `config` attributes `exploration_time`, `compression_time` as `Duration` | not present (derived: `time_limit * ratio`) | | |
| 19 | `instance.solve(config, progress=None)`; `config` mandatory | `instance.solve(config=None, *, initial_solution, on_event, events, on_interrupt)` | warm start, events | `config` defaults to `SolverConfig()` |
| 20 | `ProgressQueue`, `ReportType`, tuple `(report_type, solution)` | `on_event` callbacks, `spyrrow.events`, `ReportKind`; variants renamed (`ExplFeas` -> `EXPLORATION_FEASIBLE` ...) | typed events, sparrow listener parity, no polling thread | callback that does `queue.put(event)`; `ev.kind`/`ev.solution` |
| 21 | `StripPackingSolution(width, density, placed_items)` | adds `strip_height, feasible, run_time, seed, interrupted`; frozen | observability | additive except frozen |
| 22 | Ctrl-C silently returns a partial solution | raises `SolveInterrupted(KeyboardInterrupt)` with `.solution` | standard Python behaviour | `on_interrupt="return"` |
| 23 | `ValueError` / `RuntimeError` | `InvalidInstanceError(ValueError)`, `SolverError(RuntimeError)`, ... | precise `except` clauses | none needed (subclasses) |
| 24 | `to_json_str()` = private serde dump of Rust structs (Duration as `{secs, nanos}`, `allowed_orientations`) | sparrow/jagua external format; configs have `to_dict` only | interoperable with the sparrow CLI, loadable | use `spyrrow.v0` if the old shape is parsed somewhere |
| 25 | narrow-concavity closing disabled (spyrrow kept it `None`) | enabled with sparrow's default `(0.01, 0.01)` via `ShapeConfig` | follow sparrow defaults; benchmark parity | `ShapeConfig(narrow_concavity_cutoff=None)` **[MAINTAINER]** |
| 26 | item larger than strip detected only at/after solve | `InvalidInstanceError` at construction naming the item | TODO.txt | none |
| 27 | polygon validity errors at `solve` | additionally `instance.validate()` | | |
| 28 | `spyrrow.spyrrow` native module, `.pyi` at repo root | native module `spyrrow._core` (private) | mixed layout | do not import `_core` |
| 29 | `__version__` = Cargo version | PEP 440 distribution version | | |
| 30 | wheels per interpreter, PyPy classifier | abi3 `cp310-abi3` wheels, no PyPy **[MAINTAINER]** | build time | none for CPython users |

## 5. Compatibility strategy for the 0.x API

**Chosen: 1.0 at top level, the untouched 0.x API as `spyrrow.v0`.**

* `import spyrrow.v0 as spyrrow` is a one-line migration: same classes, signatures,
  defaults, return types, `to_json_str` output, exceptions. Verified by running the
  complete 0.x test-suite unchanged except for this import (`tests/v0/`).
* Importing `spyrrow.v0` emits a `DeprecationWarning` (once per process, i.e. at first
  import) saying it will be removed in 2.0, pointing to `MIGRATION.md`.
* `spyrrow.v0` is **frozen**: bug-fix and sparrow-sync only, no features. It runs on
  the same solver build (so it benefits from sparrow updates), but its Python API
  never evolves.
* Accessing a removed 0.x name at top level (`spyrrow.StripPackingConfig`,
  `ProgressQueue`, `ReportType`) raises an `AttributeError` that names the
  replacement and the `spyrrow.v0` escape hatch.
* Removal planned for **2.0** (suggest: not before 12 months after 1.0 final).

Alternatives considered:

| Option | Verdict |
|---|---|
| **A. Pin only**: users stay on `spyrrow<1` | Free for us, but forces users to freeze everything else (sparrow improvements, Python wheels) and gives no incremental path. Still documented as an option, not a plan. |
| **B. `spyrrow.v0` namespace (chosen)** | One-line, incremental, per-module migration (`v0` and `1.0` can even be mixed in one program), static analysis works, deletion in 2.0 is trivial. Cost: a frozen module to carry. |
| **C. Keep the 0.x names at top level with warnings, new API in `spyrrow.v1` / `spyrrow.next`** | Never breaks anyone at upgrade time and is the most "polite", but the new API would be second class, the same class names would mean different things in the two modules, and 1.0 would not really be a break (so it would not fix the pain points). Rejected. |
| **D. Evolve 0.x in place with additive 1.x releases** | Cannot remove the sentinel semantics (`None` = free rotation) or move `min_items_separation`. The goal needs a major break. |
| **E. Separate distribution (`spyrrow-legacy`)** | Doubles release/CI burden and the name space on PyPI for little gain. |

## 6. Mapping of sparrow concepts that are *not* exposed

| sparrow / jagua | status |
|---|---|
| `SeparatorConfig.log_level`, `LOG_LEVEL_FILTER_*` | not exposed (logging bridge proposed, section 8) |
| `CDEConfig.item_surrogate_config` | not exposed yet (`SPSurrogateConfig` is deep implementation detail) |
| `SparrowConfig.rng_seed` | `SolverConfig.seed` |
| `n_workers` per phase | one `num_workers` |
| `min_quality`, holes, multipolygons, containers with zones | rejected by jagua for SPP items |
| SVG export, live SVG, CLI flags | out of scope (sparrow compiled with `only_final_svg`, nothing is written) |

## 7. Testing strategy

* `tests/v0/`: the 0.x tests, only `import spyrrow.v0 as spyrrow` changed. They are
  the contract for the compatibility layer.
* `tests/test_*.py`: new API; short budgets (<= 10 s, `num_workers <= 2`): model
  validation (pure Python, instant), JSON round trips, rotation modes, reflection
  (geometric validity of transformed shapes inside the strip), warm start, events,
  stop/interrupt, errors, defaults-vs-sparrow drift, v0 deprecation warning.

## 9. Open questions for the maintainer

1. **Pre-release first (`1.0.0a1`) or straight to `1.0.0`?** Draft: alpha.
2. **abi3 / dropping PyPy** (section 2).
3. **Default rotation of `Item`**: `Rotation.none()` (draft) vs required argument vs
   continuous. 0.x forced a choice; I think silently allowing arbitrary rotation is the
   riskiest for real manufacturing parts (grain, patterns).
4. **Flat `rotation=` / `reflection_axes=` on `Item`** (draft) vs a nested
   `orientation=Orientation(rotation, reflection_axes)` like jagua's JSON. A bool
   `reflectable=True` shortcut is easy to add on top.
5. **Frozen value objects**: OK to lose mutability (`item.demand = 3`)?
6. **`num_workers=None`**: all logical cores (0.x) or capped (TODO.txt: "no more than 3/4
   workers")? Sparrow's default is 3. Needs benchmark data.
7. **Narrow-concavity closing** default: sparrow's (draft) or 0.x's `None`.
8. **Presets**: are `AUTO` / `EXHAUSTIVE` the right names and set? Which others do you
   want (`QUICK`, `GREEDY`)? What should they change?
9. **Callback delivery model**: callbacks run in the `solve()` caller thread
   (draft). Is a background-thread/`Future` handle (`instance.solve_async`) wanted?
   `StopSolving` as exception vs return value.
10. **Ctrl-C semantic**: `SolveInterrupted(KeyboardInterrupt)` with `.solution`
    (draft) vs plain `KeyboardInterrupt`.
11. **Item ids**: `int | str` with labels in JSON (draft), or `int` only like jagua, or `str` only.
12. **Empty instance**: keep returning an empty solution (draft/0.x) or raise like jagua?
13. **v0 policy**: removal in 2.0; should v0 keep receiving sparrow bumps, or be
    pinned to a last working sparrow? (Draft: shares the build.)
14. **Deprecation warning category**: `DeprecationWarning` (hidden outside `__main__`
    by default) vs `FutureWarning` (always shown).
15. `solve` only as method (draft) or also a module-level `spyrrow.solve(instance, ...)`.
16. Reflection is not used by sparrow 0.3.0 (section 3.2): keep it in the 1.0 API as a documented
    no-op, or hide it until upstream supports it?
17. Docs hosting for two API versions, and CI cost of running the (slow) `tests/v0`
    suite on every platform.
